## Archived change: `portal-miembros` (2026-09-14, DONE)

A second, separate SDD change — not part of `evolucion-plataforma-arca`, run to completion in one session and archived. Added two things: (1) an admin-only panel showing a member's full payment history (paid + pending `cargos`, all `registro_pagos`, works for retired members too — previously only pending charges were visible, as a side-effect of the payment form); (2) a public, no-login, per-member private view (`/mi-cuenta/?token=...`) where a member holding a unique link sees their own debts/contributions, backed by a new `api/member-view.ts` cloning the `api/debt-view.ts` pattern from `evolucion-plataforma-arca` Phase 3.

**This explicitly reverses `evolucion-plataforma-arca`'s own round-1 research decision** ("2-role model, no member login") — recorded as a deliberate, project-owner-confirmed override, not an oversight. The chosen mechanism is a **bearer token, not a login**: a 256-bit CSPRNG token, base64url-encoded, hashed with SHA-256 (no salt/KDF — justified in design.md D10, high entropy makes a slow KDF pointless and would force a full table scan) and stored **hash-only** on `miembros.token_hash` (+ `token_generado_en` for the UI's "Generado el ..." label). No email, no password, no new Supabase Auth surface — this was the deciding factor, since `miembros` has zero contact info and Phase 0 of `evolucion-plataforma-arca` closed public self-signup after a real incident.

- **Security properties, all independently verified live in production, not just in tests**: missing, malformed, unknown, and revoked tokens all return the exact byte-identical `404 {"error":"not_found"}` (no enumeration oracle); every response — success or failure — carries `Cache-Control: private, no-store`; `mi-cuenta/index.html` has `<meta name="referrer" content="no-referrer">` and a real-Chrome-tab check confirmed `document.referrer` is empty after following the link to `/vista/` (the token never leaks via the `Referer` header); `crypto.timingSafeEqual` is length-guarded; a 30-sample timing comparison between an unknown and a revoked token (both real live requests against production) showed medians within normal network noise of each other (~0.47s vs ~0.53s), confirming they're not distinguishable by response time, unlike the intentionally-faster missing-token short-circuit (~0.33s, accepted asymmetry).
- **Excluded from the member's own view, by spec, not just by design choice**: `motivo` (why they were charged) and `observaciones` — inherited transitively from `api/debt-view.ts`'s own confidentiality-motivated exclusion list (these can be medical/personal reasons concerning a third party). Revisiting this needs a spec amendment, not just a product sign-off.
- **Delivered as 4 chained PRs** (`auto-chain`/`stacked-to-main`, this project's cached delivery strategy): PR1 admin history (no DB), PR2 live DB schema (additive, sign-off gated, applied live 2026-09-14), PR3 token issuance UI, PR4 the public endpoint + portal page. Each PR passed an independent fresh-context adversarial verification before merge.
- Archived at `openspec/changes/archive/2026-09-14-portal-miembros/`; its three new capabilities (`member-payment-history`, `member-access-token`, `member-private-view`) now live in `openspec/specs/` alongside `evolucion-plataforma-arca`'s seven (still open, not yet archived).
- **Known operational gap, not a code gap**: no in-app way to deliver a member's link (no email/phone on file) — the admin generates it, copies it, and sends it out-of-band (WhatsApp, printed, verbal). Losing a link means the admin regenerates (the old one is immediately dead) — there is no recovery path, by design (hash-only storage).

## Change: `caja-y-transferencia` (merged to `main`, LIVE in production, NOT yet archived)

A third, separate SDD change — not part of `evolucion-plataforma-arca` and distinct from the archived `portal-miembros`, though it builds on both (it extends the Phase 3 public debt-view surface and mirrors the `portal-miembros` CLABE/token affordances). It shipped three things: (1) a **derived cash-on-hand ledger ("Arca")** computed on read from existing and new ledger rows; (2) a **CLABE copy button** on the public no-login view (`vista/`), backed by a dependency-free `src/lib/clipboard.ts` so the public bundle gains no Supabase import; (3) an admin **caja/Arca module** (opening amount + breakdown + the single disbursement capture surface described below). Its delta specs cover two capabilities: `caja` and `public-clabe-copy`.

**Core domain rule to preserve**: `Arca (disponible) = Apertura + Σ(registro_pagos.monto_pagado) − Σ(registro_apoyos.monto_total) − Σ(registro_egresos.monto)`, computed by the pure `computeCaja` — there is **no stored running balance** anywhere. An **apoyo is a LOAN**: cash leaves, a receivable is created, and members repay it through `registro_pagos`, so a fully repaid apoyo nets to zero (and an unrepaid one leaves the Arca negative). An **egreso is an EXPENSE**: cash leaves and never returns. The decisive test is *"does the money come back?"* — which is exactly why the two outflow cards (`Apoyos entregados (recuperables)` and `Egresos (no recuperables)`, grouped under "Salidas del arca") are separate and must **never be merged**. **"Por cobrar" is contextual and is never summed into the balance.**

**Naming**: "Arca" / "Arca (disponible)" is a PRESENTATIONAL user-facing label only. Internal identifiers deliberately keep their names — `computeCaja`, `cajaCents`, `src/features/caja/`, `configuracion_caja`, `#caja-content`, `fetchCaja`, `initCaja`. The UI-says-Arca / code-says-caja asymmetry is INTENTIONAL; do not "fix" it by renaming identifiers or DOM ids.

**Single capture point**: leaving the arca has exactly ONE entry surface — "Solicitud de Apoyos" — with three modalities: group (`TODOS`/`FULLPARCH`), individual (`INDIVIDUAL`), and "Sin cargos — absorbido por el Arca (no recuperable)". The last writes one `registro_egresos` row and NO apoyo and NO cargos, with an OPTIONAL beneficiary. The **Arca page is a query/config surface only** (opening amount + breakdown); its duplicate "Registrar Egreso" form was removed (commit `f94757a` — see the closure section; it is not yet on `main`).

**Internal members**: `miembros.status` gained a third value `'interno'` (widened by a live migration). An internal member is excluded from every debtor surface (admin ranking + "Miembros con Deuda" KPI, public ranking, "Por cobrar") and from group divisions; it remains selectable for individual disbursements, and it is the usual BENEFICIARY of a non-recoverable expense.

**One debt aggregation**: the admin dashboard, the public view and "Por cobrar" must produce IDENTICAL per-member figures. They previously disagreed by cents because the dashboard had its own float reduce; the dashboard now reuses the pure `aggregateDebtByMember` over `estado='pendiente'` cents. **Two screens showing two numbers for the same debt is unacceptable for an auditable ledger.**

**Migrations applied live** (same operator-run + read-back pattern as Phases 0/2/3/4, each headed with its own pre-DDL guard, each with a `_down` reversal): `supabase/sql/phase5_egresos.sql`, `phase6_miembros_status_interno.sql`, `phase7_egresos_beneficiario.sql`, `phase8_reclasificar_gasto_sin_cargar.sql`. Note: these `phaseN_` filenames continue the numbering from `evolucion-plataforma-arca`'s Phase 4, but they belong to THIS change — they are not phases of `evolucion-plataforma-arca`. Phase 8 moved ONE misrecorded disbursement from the loan ledger to the expense ledger (guarded, atomic `begin;…commit;`, reversible); the Arca balance was unchanged because both are deductions — only the classification moved, and a phantom cargo disappeared.

**Status**: merged to `main` and LIVE on production; artifacts under `openspec/changes/caja-y-transferencia/`. The change is **NOT yet archived**.

**First command in a new session**: `gentle-ai sdd-status caja-y-transferencia --cwd <repo> --json --instructions` — same authoritative-JSON-first rule as for `evolucion-plataforma-arca` above; trust its JSON over any prose, including this file.

**What remains**: the change's own artifacts need a coherence sync, then verify + archive, plus one pending commit. See "What's next: close out `caja-y-transferencia`" below.

## Vercel deploy safety — NEVER promote a mid-chain preview to Production

This file previously asserted "this project pushes straight to `main`, there's no separate preview-deploy flow in use". **That is no longer accurate and it is dangerous.** Vercel DOES produce a preview deployment per branch.

**The incident it caused**: in one session a **mid-chain preview deployment was promoted/rebuilt as Production**, so production served an unreviewed, mid-chain feature-branch commit while `main` was untouched and both PRs were still unmerged. Because the deployed code predated the formula change that adds the apoyo-deduction term, the site publicly displayed a cash figure roughly **ten times** the real value. (Figures deliberately not recorded here — this repo is public.) It was fixed by merging the PRs so Vercel deploys `main`.

**Rule, stated explicitly**: in this project, never promote a mid-chain preview to production. Merge to `main` and let Vercel deploy `main`. Do NOT tell a future session to "click Redeploy" without naming precisely which button — the same menu contains options that rebuild a deployment AS production, which is exactly how the incident above happened.

This tripped four times in one session; treat a suspiciously clean result as suspect, not as done.
- **The ledger charges TRACKED DOCUMENTATION to an attempt's budget too.** Once a change's `openspec/` artifacts are committed, every phase pays for the artifact it rewrites (one verify attempt measured 157 changed lines against an 80-line cap). Budget accordingly, and prefer setting the cap from a MEASUREMENT rather than an estimate — and note the repo's own convention above: ask the project owner before a `sdd-attempt reset`, never self-authorize.
